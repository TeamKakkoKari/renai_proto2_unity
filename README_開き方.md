## リポジトリから開く方法（推奨・半自動の更新フロー）

このプロジェクトは GitHub リポジトリ（TeamKakkoKari/renai_proto2_unity、プライベート）で管理されています。開発側の更新はすべてここへ随時 push されるので、zip を受け取る必要はありません。

※プロジェクトの設計方針・決定事項・現在の状態は **`HANDOVER_引き継ぎ.md`** にまとめてあります。初めて触る方（協力者）は、先にそちらを読んでください。

**初回のみ（詳しい手順）**

A. GitHub Desktop の準備
1. desktop.github.com から GitHub Desktop をダウンロードしてインストール
2. 起動したら「Sign in to GitHub.com」を選び、TeamKakkoKari のアカウントでサインイン（このリポジトリはプライベートなので、サインインしないと見えません）

B. リポジトリをクローン（複製）する
1. メニューの「File」→「Clone repository...」を開く
2. 「GitHub.com」タブで `TeamKakkoKari/renai_proto2_unity` を選択
3. 「Local path」に保存先フォルダを指定（例: ドキュメント\GitHub\renai_proto2_unity）
4. 「Clone」を押す（数十秒〜数分でダウンロード完了）
   ※ ブラウザでリポジトリページを開き、緑の「Code」→「Open with GitHub Desktop」でも同じことができます

C. Unity で開く
1. Unity Hub を開く（無ければ unity.com からインストール）
2. 「Open」の横の ▽ →「Add project from disk」で、クローンしたフォルダ（Assets や ProjectSettings が入っているフォルダそのもの）を選択
3. 推奨バージョンは **Unity 2022.3 LTS**。入っていない場合は Hub の「Installs」→「Install Editor」から 2022.3.x を追加してください（違うバージョンでも開けますが初回に変換が入ります）
4. プロジェクトを開く（初回は Library の自動生成で数分かかります）
5. 下部の Project ウィンドウで `Assets/Scenes/Main.unity` をダブルクリックしてシーンを開き、画面上部中央の ▶（再生）ボタンで実行
6. Game ビューの比率は 16:9（または 1280×720）にすると想定通りのレイアウトになります

**更新を受け取るとき（2回目以降）**
1. Unity の再生を止めておく
2. GitHub Desktop で左上の「Current Repository」が renai_proto2_unity になっていることを確認し、上部の「Fetch origin」を押す
3. 新しい更新があるとボタンが「Pull origin」に変わるので、それを押す
4. あとはいつも通り Unity Hub で開くだけ（変更分は自動で読み直されます）。左側の「History」タブで v14 などの版数も確認できます

※ こちら側でファイルを編集・保存していると Pull が止まることがあります。その場合は「Changes」タブでファイルを右クリック→「Discard Changes...（変更を破棄）」してから Pull してください。Unity のバージョン違いで ProjectVersion.txt が書き換わった場合も同じ操作で戻せます。基本は開いて再生するだけの使い方が安全です。

## 開き方（zipで受け取った場合）

1. Unity Hub を開く
2. 「プロジェクトを開く（Add / Open）」で、このフォルダ（renai_proto2_unity）を選択
3. 推奨バージョン: **Unity 2022.3 LTS**（それより新しいUnityでも開けますが、初回に変換が入ります）
4. 初回はインポートに少し時間がかかります
5. `Assets/Scenes/Main.unity` を開いて、上部の ▶（再生）ボタンで実行できます

※ 画面比率は 1280×720（16:9）想定です。Gameビューの比率を 16:9 にするとGodot版と同じ見た目になります。

### もし Main.unity が開けない場合

1. 空のシーンを新規作成
2. 空の GameObject を1つ作る
3. その GameObject に `Assets/Scripts/MainGame.cs` をアタッチして再生

（MainGame が Canvas や UI をすべて自動で組み立てるため、これだけでも動作します）

## 遊び方（Godot版と同じ）

- タイトル → マップで地域を選択 → 物語が始まります
- 質問の場面では、制限時間（60秒）以内にカテゴリータブから単語を選んで文章を組み立て、「発言する」を押します。選んだ単語はカードとして並び、カードを押すと取り消せます
- 文法（語順・助詞・語尾）・話題の合致・中身のある発言かどうかで好感度が変わります
- 助詞によって文章の意味と解釈が変わります（例:「あなたは好き」「あなたが好き」「あなたも好き」「あなたの好き」は別の文章として扱われます）
- 画面クリック / Enter / Space で文章送り、上部バー「ログ」でバックログ表示
- 好感度は自動保存されます（Unityの persistentDataPath 内 affection.json）

## データの編集（Godot版と同一形式）

`Assets/Resources/data/` のJSONを書き換えるだけで内容を変更できます。コードの変更は不要です。

- `words.json` … 単語（カテゴリ・タグ）
- `characters.json` … キャラ・質問・反応セリフ・表情差分
- `stories.json` … 物語の台本とエンディング
- `stages.json` … 地域（背景色・説明）
- `evaluation.json` … 評価の数値と制限時間

立ち絵・表情・ワールドマップ画像は `Assets/Resources/assets/`、フォントは `Assets/Resources/fonts/`（M PLUS Rounded 1c / SIL Open Font License）にあります。

## v29 の変更点（文字の Height を大きくし、文の途切れを直す）

- ユーザーの指摘「普通に全然直ってない、Heightを大きくしなよ、じゃないと文が途切れてるって」の通り、高さの計算がきつすぎました。行高の見積もりがフォントサイズの1.32倍ちょうどで余白が0だったため、Unity の M PLUS Rounded 1c の実際の行高（1.32倍より大きい）では最下行が切れていました。名前も24pxなのに箱が28px（必要31.7px）で、下が切れていました。
- 行高の見積もりを1.32倍→1.50倍にし、性格文に余白12px、セリフに余白16px、吹き出しの下余白を12px→20pxにしました。名前の箱は28px→40px、セリフの箱は2行で82px、吹き出しは質問時261px・最長でも307pxで、パレット上端（448）より上に収まります。長いセリフだけは吹き出し高さ上限340pxを超えないようフォントを少し小さくします。
- 縦の切れ方を Truncate（高さ不足で切る）から Overflow（高さが足りなくても文字を出す）に変えました。吹き出し・発言プレビュー・評価カード・すべてのラベルが対象で、シーンに残っている Truncate も実行時に上書きします。これで高さの見積もりが多少ずれても文が途切れません。
- 初期サイズも大きくしました（吹き出し212→280px、セリフ92→150px、発言プレビュー56→84px、タイマー文字22→30pxなど）。LayoutBubble が走る前の1フレーム目やシーン表示でも切れにくくなります。

## v27 の変更点（全データの中身を監査し、文字のはみ出し・切れを全体修正）

- 全データ（質問・ストーリー・反応・単語・評価）の中身を監査しました。最長の質問は31文字、最長のエンディングは57文字、最長の単語は6文字で、吹き出しの配置はすべて収まることを確認しました。セリフの最大行数を4行から5行に増やし、文字幅の見積もり誤差でも切れないよう余裕を持たせました。
- 吹き出しの配置を、シーンの値や preserveLayout の状態に左右されないよう、直接設定（SetRectForce）に変えました。さらに、表示中に配置がずれていたら次のフレームで直す安全網を入れました。スクショで報告された「森の花が咲きました。どう思いますか？」（20文字）は22px・2行で、吹き出し高さ156pxに収まります。
- 評価カードの結果欄は、理由が5〜8個並ぶと「…」で切れていました。表示は先頭3件までにして、全文はバックログに残すようにしました（最長の3件でも13px・5行で収まります）。
- タイトル画面右下の版数ラベルが、シーン生成時（v22）の「Prototype 2 v22 (Unity版)」のまま残ってしまう問題を修正しました。シーン再利用時に MkLabel がテキストを設定しないためで、実行中の版数を直接書き込むようにしました。これで、版数を見ればどの版のコードで動いているか分かります。
- 選べる単語は12個までにしました。無制限だと発言プレビューが3行に収まらず「…」で切れ、チップもボタン列にはみ出していました。12個あれば十分な長さの文章が作れます。上限に達したら「単語は12個までです」と表示します。

## v26 の変更点（吹き出しの文字を枠内に収める・単語ボタンを白背景＋黒文字に）

- 吹き出しの文字が枠からはみ出す問題を根本修正しました。名前・性格・セリフ・「つぎへ」ボタンを、実行時に吹き出し本体の子にして吹き出し内座標で配置し直すようにしたため、シーンの位置がずれていても文字は必ず吹き出しの中（左右16px・上10pxの余白つき）に収まります。ナレーション（性格＋舞台説明3行＋セリフ3行）でも吹き出しが244pxまで伸びて、文字が欠けません。タイプライターが自然に終わったときも、表示完了時の再レイアウトが走るようにしました。
- 単語ボタン・タブ・チップ・小さい操作ボタン（◀ ▶ 削除・一つ戻す・全解除・ページ送り）を、白背景＋黒文字にしました。選ばれているものは淡い緑で示します。「発言する」ボタンは緑のまま（メインの操作のため）、発言パネルは紺色のままです。白いボタンがクリーム色のパネル上で溶けて見えないよう、ボタンには2pxの灰色の枠線を入れました。

## v25 の変更点（ボタン・上部バー・タイマーの読みやすさを全体修正）

スクリーンショットで確認された、質問フェーズの画面全体が見づらい問題を修正します。

- 単語ボタン・タブ・「発言する」ボタンなどの背景が消え、白文字がクリーム色のパネルに溶けて読めなかった
- 上部の好感度・面白さのピルに背景がなく、明るい背景写真の上で白文字が読めなかった
- 吹き出しの名前が見えにくく、セリフで人名（リーリア）が行またぎで割れていた
- タイマーの文字とバーが立ち絵や背景写真の上に直接置かれていた

原因は2つです。

1. 角丸スプライト（RoundedSprite）のボーダーが26pxで、上下合計52pxあるのに、ボタンの高さは29〜54pxしかなかったため、Sliced 描画が潰れて背景が1pxの線にしかならなかった（パネルは高さが大きく、潰れなかったので正しく見えていた）
2. Button の ColorTint が normalColor（白）で Image の色を上書きし、設定した紺色のボタンが白くなっていた。さらにパレット側で1.0を超える色（1.18f）を指定していたため、白に潰れていた

修正内容は次の通りです。

- 小さい部品用に角半径10px・ボーダー10pxのスプライト（ButtonSprite）を追加し、すべてのボタン・ピル・上部帯・検索欄に使う。パネル（吹き出し・発言パネル・パレット）は従来のスプライトのまま
- Button の遷移（ColorTint）をやめ、色は Image の色で直接決める。1.0を超える色指定を削除
- 上部帯を60px・不透明度0.95にし、ピルを44px・白文字15pxに。タイトルを18px・白に
- 吹き出しを388pxに広げ、名前・性格・セリフ・ボタンの描画順を上から固定し、名前が隠れないようにする。人名が行またぎで割れる場合はフォントを1pxずつ縮小する（リーリアの質問は20px・2行で名前が1行に収まる）
- タイマーの文字とバーを濃い帯の上にまとめ、バーを12pxに太くする
- 選択中の単語・タブ・「発言する」ボタンの緑を濃くし、白文字のコントラストを6.3:1以上にする。非選択タブの文字も白に。ヒント文・ページ表示・検索のプレースホルダーを濃い色に

検証：全キャラクターの質問（20件）は20〜22px・1〜2行で人名の行またぎなし。ナレーション（最長35字）は22px・3行以内。性格文は13px・2〜3行。単語ボタンの白文字と紺色背景のコントラストは13.8:1。

シーンUIについて：main にシーン生成コミット（"UIをシーンに生成"）が入ったため、v25ではシーン再利用時もスプライトとボタンの遷移だけは実行時に直すようにした。位置・大きさ・色はシーンの手動編集を尊重するが、読みやすさのための色（発言ボタン、ヒント文、ページ表示、検索プレースホルダー、好感度・面白さの文字、性格文）だけは実行時に上書きする。コード生成のみの場合は、すべての修正がそのまま適用される。

## v23 の変更点（吹き出しの文字が枠外にはみ出す問題を自動フィットで修正）

グリムのナレーション画面のスクリーンショットで、吹き出しの性格文が1行で切れて枠外に出る、セリフが小さく1行に詰まって「た。」だけ2行目に落ちる、「つぎへ ▼」ボタンが吹き出しの下端に来る、という問題が確認されました。原因は Unity の BestFit（文字を枠に合わせて自動で縮小する機能）が、日本語の太字を1行に詰めようとしてフォントを小さくし、枠幅より広い1行を作ってしまうことです。

**直し方（BestFitに頼らず、文字量からフォントサイズと行数を自分で決める）**
- 全角1文字＝フォントサイズ×1.08、半角＝×0.58で文字幅を見積もり、枠に収まる最大のフォントを選びます（`MainGame.cs` の `FitFontForBox` / `SetFittedText`）。収まらない場合は末尾を「…」で切り、枠外には絶対に出しません
- 吹き出しの高さを中身に合わせて組み直します（`LayoutBubble`）。グリムの例では性格文61字が12px・3行、セリフ26字が22px・2行、吹き出しの高さは約212pxになります。タイプライター表示中も、フォントサイズと高さは全文で決めて固定するので、表示中に文字の大きさが変わりません
- 発言プレビューも同じ仕組みで最大3行まで高さを伸ばし、発言ボタンをその下にずらします（`LayoutSentence`）。単語ボタンの「×2」は、入らない場合はフォントを11pxまで縮めます
- 上部に濃い帯（高さ56px）を追加し、タイトルと好感度・面白さピルが背景や立ち絵の上に浮かないようにしました。立ち絵は帯の分だけ下げ（y=8→56）、幅上限を380→320pxにして、表情差分が発言パネルの下に潜らないようにしました

**v22のシーンUIとの関係（重要）**
- 吹き出し・発言プレビューの自動フィットは実行時に適用されるので、シーン再生成なしでも直ります。ただしこの2か所だけは、実行時に位置・大きさ・フォントサイズを計算で上書きします（シーンで手動編集したこれらの値は、再生時に自動フィットで置き換わります）

- ゲームのロジック（単語の追加・削除、評価、好感度計算）は変更していません

## v22 の変更点（UIをヒエラルキーで手動編集可能に）

これまでUIは実行時にコードで組み立てていたため、Unityエディタのヒエラルキーには何も残らず、手動で位置や色を変えることができませんでした。v22から、UIをシーンに実体化して手動編集できるようになりました。

**使い方**
1. Unityで `Assets/Scenes/Main.unity` を開く
2. 上部メニューの **「RenaiProto2」→「UIをシーンに生成」** を実行する
3. ヒエラルキーに **Canvas → Root** 以下、UIの全オブジェクト（名前付き）が並ぶ
4. シーンを保存（Ctrl+S）する

**編集の仕方**
- ヒエラルキーでオブジェクト（例：`SpeechBubble`、`SpeakButton`、`AffectionPill`）を選ぶと、Inspectorで位置・大きさ・色・文字・フォントサイズを変更できます。保存して再生すれば、そのままゲームに反映されます（実行時にコードが名前で見つけて再利用し、レイアウトは上書きしません）
- ボタンのクリック動作は実行時に付け直されるので、ボタンの見た目や文言は自由に変えて大丈夫です
- **名前と階層（親子関係）は変えないでください**。名前で探せなくなると、その部品だけ初期配置で作り直されます
- 単語ボタン・選択チップ・タブ・バックログの行など、データに連動して増減する部品は今まで通り実行時に自動生成されます（置き場所の枠＝`Palette`、`Tabs`、`Chips`、`Content` はシーン側で編集できます）
- 数値で連動する部分（好感度バーの中身の長さ、タイマーバーの残量、立ち絵の表示サイズ）は実行時に計算されるため、その部分の手動変更は再生時に上書きされます

**元に戻したいとき**
- ヒエラルキーの `Canvas` を削除してシーンを保存すれば、従来通りコード生成だけの動作に戻ります（ゲームは壊れません）
- もう一度「UIをシーンに生成」を実行すると初期配置で作り直せます（確認ダイアログが出ます。手動編集は消えます）

※開発側ではUnityエディタを実行できないため、この生成処理の実機確認は未実施です。実行時にエラーや表示の崩れが出たら、スクリーンショットを送ってください。

## v10 文章解析システム（助詞・接続語）

発言は `SentenceAnalyzer.cs` が助詞をもとに解析し、好感度の評価（Evaluator）とは**独立に**判定します。

- **助詞の役割**: は=話題、が=主語、を=動作の対象、に=受け手・方向、と=共同する相手、も=追加、の=所有・関係、で=場所・手段、へ=目的地、から=起点、まで=終点、や=並列。文末の「か/ですか」は質問、「してください」は依頼として扱います
- **関係の構築**: 「あなたと森へ行きたい」→ あなた（共同する相手）・森（目的地）のように、単語同士の関係を組み立てて意味を推測します
- **複数解釈の許容**: 「あなたが好き」「あなたの好き」のように複数の読み方ができる文は解釈候補を複数持ちます。好感度が高い相手の発言は好意的に解釈されやすく、決められない場合はキャラクターが聞き返します（専用セリフ「clarify」）
- **理解度Lv1〜4**: 1=自然、2=多少不自然だが推測可能、3=複数の解釈が可能、4=理解が困難。理解度と好感度は直接結びつけていません（不自然でも面白い文はあります）
- **現実には難しい関係**: 「リンゴと結婚してください」のような文は、失敗扱いではなく笑いの反応（専用セリフ「absurd」）になります
- 解析結果（関係・解釈・理解度）は、発言後に「ログ」で確認できます

単語は103語に増えました（助詞9種・文末表現6種・リンゴ/こと/結婚/あげる を追加）。助詞は質問の場面で常時提示されます。
